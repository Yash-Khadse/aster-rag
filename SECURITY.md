# Security boundary and remaining work

The API uses password hashing, signed expiring bearer tokens, tenant/workspace membership and document-level access checks. SQL metadata determines ownership; vector namespaces are an additional partition, not authorization. Only authorized current-version chunks may reach retrieval, prompts or source responses. Demo users must remain read-only.

Retrieved documents are untrusted data. Prompt framing and citation allowlists reduce accidental instruction following; they do not prove immunity to prompt injection. The corpus includes malicious text for evaluation. Never place secrets in prompts, frontend public variables or committed files.

Source downloads require API authentication. The Supabase bucket must remain private and its service key backend-only. CORS is an exact allowlist. Browser sessions use an HttpOnly `aster_session` cookie (bearer tokens remain for API clients), so page scripts cannot read the token; cookie-authenticated unsafe requests require `X-CSRF-Token` = HMAC-SHA256(`JWT_SECRET`, session JWT), compared in constant time. CORS is credentialed, so `CORS_ORIGINS` must be explicit origins (`*` fails startup). Cross-site caveat: a hosted frontend and API on different registrable domains need `SameSite=None; Secure` cookies, which Safari/Firefox ITP and third-party-cookie blocking may drop; serve both under one parent domain (e.g. `app.example.com` and `api.example.com`). Still recommended: CSP, password reset and MFA.

Uploads are size/type bounded and parsed without executing embedded scripts. This is not a malware scanner. Before arbitrary public uploads, add antivirus scanning, parser sandboxing, CPU/memory/time limits, PDF decompression/page limits and abuse monitoring. OCR remains an explicit unavailable case when no OCR service is configured.

Auth lifecycle: bearer tokens carry a per-user `token_version`; logout and password change bump it and invalidate every outstanding token, and removing a member stops their tokens in that workspace immediately (membership is checked per request). Login verifies a dummy hash for unknown accounts to blunt timing probes. Email verification (`REQUIRE_EMAIL_VERIFICATION`, default on when hosted, needs `SMTP_HOST`/`WEB_URL`): unverified accounts cannot log in or be added as members; only a sha256 of the emailed token is stored, valid 24 hours, single use. Not implemented: password reset and MFA; resend is limited only by the per-IP auth limiter (no per-account cooldown). The auth rate limiter is in-process and per replica; behind a reverse proxy set `TRUST_PROXY=true` (last `X-Forwarded-For` hop, exactly one trusted proxy) or all clients share the proxy's address. Unknown `ENVIRONMENT` values fail at startup; `hosted` additionally requires PostgreSQL, Supabase storage, Pinecone and an explicit 32+ character `JWT_SECRET`. Per-workspace document and byte quotas bound uploads, but the multipart body is still spooled before the size check on requests without a `Content-Length`.

Operational hardening still required: independent penetration review, distributed rate limiting across replicas, centralized redacted audit export, backup/restore drills, secret rotation, dependency monitoring, retention/deletion verification, encrypted transport everywhere, and resource monitoring. A role name or checklist does not establish SOC 2, HIPAA or GDPR compliance.

Run cross-tenant and unauthorized-source tests before deployment. Do not log source text, tokens, passwords or provider keys. Report security issues privately to the repository owner; no public disclosure contact has been configured yet.
